## Target Application Architecture

The application remains one Next.js deployment and one PostgreSQL database. It should evolve
toward cohesive domain modules with a small shared kernel:

```text
src/
├── app/                         # routes and page composition
├── features/
│   ├── organizations/
│   │   ├── schemas.ts           # narrow runtime commands and list inputs
│   │   ├── authorization.ts     # domain-specific capability checks
│   │   ├── queries.ts           # server-only reads and DTO mapping
│   │   ├── mutations.ts         # transactions and invariants
│   │   ├── actions.ts           # thin exported adapters
│   │   └── components/
│   ├── pets/
│   └── users/
├── lib/
│   ├── auth/                    # requireUser, role, and membership primitives
│   ├── action-result.ts
│   └── pagination.ts
└── db/
    ├── schema/
    ├── migrations/
    └── index.ts
```

This tree is a direction, not a required repository-wide refactor. Each feature introduces only
the boundaries it consumes.

The enforced boundaries are:

1. Pages compose features; they do not define access policy.
2. Exported server actions validate and authorize every request.
3. Domain mutations own invariants and transactions.
4. Queries return deliberate DTOs rather than unrestricted rows.
5. Drizzle is the application-data access mechanism.
6. Supabase provides Auth, Storage, and selected Realtime capabilities.
7. Cross-tenant access is constrained in authorization logic and SQL.

No separate REST or GraphQL layer is needed until a real external client requires it.

## Reference CRUD Contract

Before adding another entity, Organizations should prove this contract end to end.

### List

- Parse page, limit, sort, and filters through a narrow schema.
- Enforce read scope before querying.
- Apply filters before count and pagination.
- Select only list DTO fields.
- Use deterministic ordering with a unique tie-breaker.
- Return normalized pagination metadata.

### Detail

- Validate the identifier.
- Apply tenant and ownership constraints in the query.
- Return not-found for inaccessible records when disclosure matters.
- Return a detail DTO instead of the raw row.

### Create

- Parse a narrow create command and reject unknown fields.
- Authorize the target scope.
- Map database conflicts to stable expected errors.
- Set identifiers, tenant ownership, audit actor, and timestamps on the server.
- Use a transaction for local multi-table changes.
- Revalidate the smallest relevant path or tag.

### Update

- Parse a narrow update command.
- Constrain the update by authorized scope.
- Enforce allowed transitions and role-dependent fields.
- Prevent reassignment of tenant, identifiers, and audit fields.
- Add optimistic conflict detection only where concurrent overwrites matter.

### Archive or delete

- Authorize the exact destructive operation.
- Check dependencies.
- Prefer archive or status transitions for historical business data.
- Record sensitive operations when the audit capability exists.
- Return an idempotent typed result.

### Action result

Expected domain failures should use a stable serializable result rather than parsing thrown error
messages:

```ts
type ActionResult<T> =
  | { ok: true; data: T }
  | {
      ok: false;
      code: 'VALIDATION' | 'UNAUTHORIZED' | 'FORBIDDEN' | 'NOT_FOUND' | 'CONFLICT';
      message: string;
      fieldErrors?: Record<string, string[]>;
    };
```
